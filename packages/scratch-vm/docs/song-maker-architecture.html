Song Maker — synthesis & timing engines

How notes get from the editor and Scratch blocks to the speakers, and where the structure starts to fight us.

The Song Maker is two engines wrapped in one singleton. A timing engine decides when notes happen (a 25 ms tick loop scheduling 100 ms ahead of audioContext.currentTime) and a synthesis engine decides how they sound (a per-track Web Audio FX chain fed by either a synth voice or a sample voice). Both live behind runtime.songPlayback, a single project-wide instance shared by the editor preview and the Scratch extension blocks (lazy-init at runtime.js:428-434).

Two structural problems this doc walks through:
  • Block effect/volume writes mutate editor state. The set [track] [param] to [value] block writes directly into track.effects/track.volume on the shared runtime.song object. The editor reads from the same object, so block changes appear in the sliders and get serialized into the project. Block-driven changes should be a temporary live override, not a write-through.
  • Editor volume slider hitches. Track volume isn't on any audio node — it's a per-scheduled-note multiplier. Each pixel of slider drag goes through a Redux _commit({tracks}), a full song re-render, and an eventual _flattenNotes() rebuild. What should be one gainNode.gain.setTargetAtTime() call is doing a full state round-trip.

1. Big picture

Three "writers" mutate the same runtime.song; one playback singleton holds at most one scheduler; that scheduler talks to Web Audio.

Both the editor's preview transport and the extension's play [track] block route through the same SongPlayback — there's only ever one transport running.

2. Data model

The song is one JSON-shaped object hanging off runtime.song. Everything in it is serialized into the project; the scheduler keeps a small amount of runtime-only state on the side (active tracks, glide history, pending changes) that is not persisted.

runtime.song = {
  songId, name, tempo,            // tempo in BPM (default 120)
  lengthSteps, stepsPerBeat,      // default 32 steps, 4 steps/beat → 16th-note grid
  tracks: [
    {
      trackId, name, kind,        // 'synth' | 'drum' | 'instrument'
      instrument | drum | drumLanes,
      volume,                     // 0..100  ← read per-scheduled-note (issue B)
      muted, solo,
      effects: {                  // ← block writes land HERE too (issue A)
        reverb, delay, filter, pan, distortion   // 0..1, pan -1..1
      },
      synth: { osc1Wave, osc2Wave, oscMix, filterCutoff,
               filterResonance, filterEnvAmount, ampAttack…,
               lfoRate, lfoDepth, lfoDest, glideTime, … },
      notes: [ { step, pitch | drum, durationSteps, velocity } ]
    }
  ]
}

// runtime-only (lives on the scheduler, not persisted):
scheduler._activeTracks       // Set of trackIds currently audible

3. Timing engine

The scheduler does lookahead scheduling against audioContext.currentTime — the same approach as the canonical "A Tale of Two Clocks" pattern. A JavaScript setInterval wakes up every 25 ms; on each wake-up the scheduler enqueues every note that should sound within the next 100 ms using source.start(when). Web Audio handles the sample-accurate delivery; JS just has to stay ahead of the cursor.

Anchor: _startCtxTime = now + 0.05 − (startStep × sps). A note's wall-clock time is iterStart + (note.step × sps). The transport idles out automatically when the active set empties.

4. Synthesis engine

Each track lazily builds a single FX chain the first time it plays a note (_getTrackChain). All voices on that track — whether subtractive synth or sample-based — feed into chain.input and are shaped by the same downstream EQ/spatial effects.

Per-track FX chain

Effects sliders animate the parameters on these existing nodes via setTargetAtTime(value, now, 0.02) — no node teardown, no glitches. Built once per track, reused for every note.

Synth voice (built fresh per note)

_scheduleSynthNote. Glide between consecutive notes uses _lastPitchByTrack to ramp pitch over glideTime.

Sample voice (instruments & drums, built fresh per note)

_scheduleNote for drums and pitched instruments. Track volume is currently baked into the per-note volumeGain at scheduler.js:307 and :655 — that's the lever issue B wants to relocate.

6. Issue A — Block effects mutate editor state

The bug, in one line

_writeParam stores into track.effects[param] on the same runtime.song object the editor reads from. Block changes are heard live and bleed into the editor sliders and get saved with the project. There's nowhere for the "editor value" to hide once a block has clobbered it.

Reference: index.js:269-274. The _effectsCache in scheduler.js:282-288 looks like it could play this role, but today it's just a write-through copy of the same value.

Proposed shape — runtime-only override layer

Introduce a per-track override bag in SongPlayback, separate from track.effects:

  • Block _writeParam calls a new songPlayback.setTrackEffectOverride(trackId, param, value) instead of touching track.effects.
  • When the scheduler applies effects, it resolves effective = { ...track.effects, ...override } — repurpose the existing _effectsCache as the override store and drop its dual role.
  • Clear overrides on: stop() (the green-flag stop event the playback already listens to at song-playback.js:26), project load, and when the user moves an editor slider for the same (trackId, param) (editor wins back ownership).
  • Block _readParam reads the resolved value so change … by composes against what's currently audible.
  • Apply the same pattern to volume so block volume changes also don't leak.

Files to touch: index.js:261-322, song-playback.js, scheduler.js:240-288.

7. Issue B — Volume should be one gain.setTargetAtTime

The bug, in one line

Track volume isn't on any audio node — it's read out of track.volume at note-schedule time (scheduler.js:307, used to compute finalGain at :661 / :788) and baked into a per-note volumeGain. To change "the current volume" you have to update the source-of-truth on runtime.song and wait for the next note to be scheduled. The editor (song-editor.jsx:342-353) only fast-paths effects; volume falls through to Redux _commit({tracks}) + full song re-render + vm.updateSong + scheduler _flattenNotes — every pixel of slider drag.

Proposed shape — make volume a real audio node

  • Add a volume gain node to the per-track chain in _getTrackChain. Insert it at the head, before distortion — or just repurpose the existing input gain (which is currently held at 1 and only animated by fades).
  • Add setTrackVolume(trackId, v) to SongScheduler and SongPlayback, parallel to setTrackEffects: chain.volume.gain.setTargetAtTime(v, now, 0.02). Zero song mutation, zero re-flatten, zero React re-render.
  • Editor: handleVolumeChange calls player.setTrackVolume immediately for the live audio change. Persistence to runtime.song debounces (e.g. on slider change / blur, not input) so the Redux commit only happens at slider release.
  • Drop the per-note trackVol multiplier from scheduler.js:307 / :655 / :786 — the track-level gain node is now the single source of truth. (Per-note velocity stays where it is; that's musical, not a mixer level.)
  • Block set [track] volume goes through the same setTrackVolume, but writes to the override layer from issue A so block volume also doesn't leak into the project.
  • Watch out for the fade animation already on chain.input.gain (scheduler.js:433-460) — if volume and fade share a node, multiplying them via two nodes (volume × fadeGain) keeps the two automations independent.

Files to touch: scheduler.js:171-250 (add node), :307 / :655 / :786 (drop per-note multiplier), song-playback.js (expose setTrackVolume), song-player.js (forward), song-editor.jsx:342-353 (fast path + debounce commit).
