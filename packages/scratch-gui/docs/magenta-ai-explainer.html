Magenta AI in Song Maker

How it works today, what it's actually doing under the hood, and a proposal to swap the free-form prompt for structured dropdowns.

1. What is Magenta?

Magenta is a Google research library for generative music, exposed in the browser via @magenta/music (TensorFlow.js under the hood). We use two of its smallest models, both in the MusicRNN family — recurrent neural networks that take a short seed NoteSequence and "continue" it for N more steps.

  • Melody RNN — checkpoint basic_rnn. Continues a monophonic melody.
  • Drum Kit RNN — checkpoint drum_kit_rnn. Continues a drum pattern, emitting GM-MIDI drum pitches.

Both checkpoints are downloaded on first use from storage.googleapis.com/magentadata/js/checkpoints/music_rnn/. The core call is:

rnn.continueSequence(seedNoteSequence, stepsToGenerate, temperature)

That's it. There is no prompt input on the model itself. The "prompt" only exists in our UI — Magenta only sees a fixed-shape seed sequence and a temperature.

2. How it's wired into Song Maker

All Magenta code lives in packages/scratch-gui/src/lib/song-ai/providers/magenta.js. A few key bits:

  • Lazy-loaded via webpackChunkName: "magenta" (magenta.js lines 15–29) so TF.js only enters the bundle when the provider is selected.
  • Model cache keyed by checkpoint URL (getRnn, lines 39–51). One initialize per checkpoint per session.
  • Drum pitch mapping GM-MIDI → our 1-based drum indices (drumPitchToOurIndex, lines 59–74).
  • Prompt parsing keyword-spots mood / tempo / key from the textarea (parseVibe, lines 79–163).

The whole "AI understands my prompt" illusion is just keyword spotting against three dictionaries:

const MOOD_KEYWORDS = {
  happy:  ['happy', 'bright', 'cheerful', 'joyful', 'sunny', 'triumphant', 'celebrat'],
  sad:    ['sad', 'somber', 'melancholy', 'sorrowful', 'gloomy', 'mournful'],
  dark:   ['dark', 'cinematic', 'serious', 'epic', 'tense'],
  spooky: ['spooky', 'haunting', 'creepy', 'eerie', 'mysterious', 'horror', 'scary', 'ghost'],
  bluesy: ['blues', 'bluesy', 'soulful', 'gritty'],
  rock:   ['rock', 'metal', 'punk', 'grunge'],
  folk:   ['folk', 'whimsical', 'wholesome', 'kid', 'nursery', 'lullaby'],
  funk:   ['funk', 'funky', 'groovy'],
  jazz:   ['jazz', 'jazzy', 'swing', 'bebop'],
  chill:  ['chill', 'lo-fi', 'lofi', 'mellow', 'dreamy', 'ambient', 'relaxed'],
  upbeat: ['upbeat', 'energetic', 'punchy', 'driving', 'dance', 'party']
};

Anything outside these eleven moods, three tempo buckets (slow/medium/fast), and a handful of key-phrase regexes is silently discarded.

4. The problem with the prompt textarea

The textarea creates an expectation the model can't meet. Magenta is a small RNN over a fixed seed — it can't interpret language. Three concrete examples:

Prompt: "a soaring lead melody with a syncopated swing feel in F# minor"
What Magenta sees: mood = null (no keyword matches "soaring lead"), tempoBucket = null, key = F#, scale = minor. Everything else is dropped.
Prompt: "a punchy four-on-the-floor groove"
What Magenta sees: mood = upbeat (matched "punchy"), tempo = fast. "Four-on-the-floor" is silently ignored. Seed = funk pattern from DRUM_SEEDS.funk regardless.
Edit prompt: "harmonize this with 3-note chords"
What Magenta sees: none of the edit keywords (louder, softer, higher, lower, faster, slower, regenerate) match → falls through to regenerate, producing a new unrelated track. The user's intent is lost.

The textarea is fine for the LLM providers (Claude, Gemma 4, Gemini Nano), which actually do parse it. But for Magenta — the default, on-device, always-available provider — the prompt is theatre.

5. Proposed redesign

Replace the textarea with structured controls that map directly to the parameters Magenta actually consumes. Each track type gets a control set tuned to what its model can do.

5a. Drum track generation Magenta

Drum generation is driven by which seed pattern we pick from DRUM_SEEDS (rock / funk / chill) and how many steps we let the RNN continue. Both are dropdown-shaped already:

Add a drum track

On-device Magenta will generate the pattern.

Hip-hop and Latin are new seed patterns we'd add to DRUM_SEEDS alongside the existing rock/funk/chill.

5b. Instrument / synth track generation Magenta

Melody RNN is one model — what changes between "lead", "bass", "pad", "arp" is what we do around it (which builder is called, which transpose, whether we keep melody output or repurpose as chords).

Add an instrument track

On-device Magenta will generate the part.

The 11 mood options exactly mirror MOOD_KEYWORDS. Register maps to the leadRegister parameter on buildMelodyTrack (currently hard-coded to +12 semitones). Density maps to stepsToGenerate and the temperature passed to continueSequence.

5c. Edit track — continue from the user's notes Magenta

The procedural transforms (lines 513–521 in magenta.js) are a workaround for the prompt textarea — they exist because Magenta's prompt parsing doesn't understand edit instructions. But Magenta's continueSequence is literally a "given these notes, what comes next" model. Edit-track is actually its best fit in the entire app.

Proposal: drop the procedural transforms entirely. Feed the existing track's notes as the seed to continueSequence and let the RNN produce a variation that's musically related to what the user already has.

Edit "Lead synth"

Magenta will use your existing notes as the seed and generate a variation.

How the controls map to Magenta: "Seed from" controls how much of the existing track is passed to makeSeedSequence(). "Variation" maps to the temperature argument of continueSequence (0.7 / 1.0 / 1.4). "Apply as" decides what to do with the continuation — overwrite, concatenate, or merge into the existing notes.

This works uniformly for drum tracks (seeded with Drum RNN) and instrument/synth tracks (seeded with Melody RNN) — pick the model by track.kind, same as today.

What we lose: the instant velocity/pitch nudges (Louder / Softer / Up octave / Down octave). Those are useful but they aren't AI — they're regular edit operations. They'd be better off as toolbar buttons on the track row itself, separate from the "AI edit" entry point. The AI modal becomes specifically for generating a variation, which matches the user's mental model better.

5d. Whole-song modal — hybrid by provider

This is the most interesting case because the modal is shared across all providers, and the LLM providers really do interpret prose. The proposal: switch the input region based on the selected provider. Click the toggle below to see how it'd feel:

Create a song Magenta

Pick the basics — Magenta will fill in the rest.

Create a song Claude

Describe what you want — Claude can interpret freely.

The provider picker already lives in provider-picker.jsx. The hybrid is a small change in ai-song-modal.jsx: gate the input section on providerId === 'magenta'.

7. Implementation sketch

Files that would change (this doc is not yet implementing them):

  • ai-generate-track-modal.jsx — branch on kind prop, render the drum or instrument dropdown set when the selected provider is Magenta.
  • ai-edit-track-modal.jsx — replace textarea with the three-dropdown variation picker.
  • magenta.js editTrackProcedurally() — replace its body with a continueSequence call seeded from originalTrack.notes. Pick the model (DRUMS_RNN_URL vs MELODY_RNN_URL) from originalTrack.kind. The existing GM-MIDI → lane mapping (noteSeqToDrumNotes) and transpose (noteSeqToInstrumentNotes) helpers can be reused unchanged.
  • Delete the EDIT_KEYWORDS dictionary at lines 513–521 and the velocity/pitch/density branches that follow it. Consider relocating those as direct toolbar buttons on the track row.
  • ai-song-modal.jsx — hybrid: swap input region on providerId change.
  • magenta.js — accept a structured params object alongside (or instead of) prompt. When structured params arrive, bypass parseVibe and use them directly. Keep prompt-based path for any callers that still need it.

Constants we can reuse rather than redeclare:

  • INSTRUMENT_NAMES, DRUM_NAMES from song-defaults.js
  • SYNTH_PRESETS from synth-presets.js
  • PITCH_CLASS_NAMES, SCALE_LABELS from scale-utils.js

8. Open questions

  1. Should LLM providers also get dropdowns as an option? The Magenta dropdowns could double as a "quick mode" for Claude / Gemma 4 / Gemini Nano, with the textarea as an optional override. Or we keep LLMs prose-only to play to their strength.
  2. Edit modal for LLM providers? The continue-from-seed dropdowns are right for Magenta. LLM providers (Claude, Gemma 4, Gemini Nano) can interpret instructions like "harmonize with 3-note chords" or "make this swing" that go far beyond what an RNN can do — so the edit modal probably wants the same hybrid treatment as the whole-song modal: dropdowns for Magenta, textarea for LLMs.
  3. How do we serialize the dropdown selections to LLM providers? Two options: (a) pass them verbatim as structured tool input, (b) render them into a synthesized English prompt like "Style: Rock. Density: Busy. Drums: Full kit." Option (a) is cleaner; option (b) preserves the LLM's prompt-shaped expectation.
  4. Voice input — currently a mic button on the track modals. Where does it land in a dropdown UI? Drop it entirely for Magenta, keep it for LLM textarea, or have voice fill structured fields ("make it a rock drum part" → sets Style=Rock)?
